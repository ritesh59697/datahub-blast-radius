# Sample outputs

Every file here was generated by running Blast Radius against a live DataHub
instance loaded with the `showcase-ecommerce` datapack. Nothing is hand-written
or edited. Reproduce any of them with the command shown.

## PR comments, one per severity level

The point of these three is that the tool **discriminates**. A reviewer who
gets a red banner on every pull request stops reading them.

| File | Column | Severity | Why |
|---|---|---|---|
| [critical-orders.order_date.md](critical-orders.order_date.md) | `orders.order_date` | 🔴 CRITICAL | A Looker dashboard and two charts render it |
| [high-orders.order_id.md](high-orders.order_id.md) | `orders.order_id` | 🟠 HIGH | Three charts consume it, no dashboard |
| [medium-customers.nls_language.md](medium-customers.nls_language.md) | `customers.nls_language` | 🟡 MEDIUM | Only derived tables and replication jobs |

```bash
blast-radius analyze --column orders.order_date --platform postgres --format markdown
```

Severity is driven by *what* breaks, not how many things break. In this
warehouse nearly every column fans out to 3+ platforms, so counting platforms
or downstream totals rates everything HIGH and the signal disappears. A
dashboard breaking outranks twenty staging tables changing.

## Migration plan

[migration-orders.order_date.md](migration-orders.order_date.md) — the ordered
plan for actually shipping the rename: a backwards-compatible alias first, then
consumers nearest-first, each attributed to its owner from DataHub.

```bash
blast-radius analyze --diff pr.diff --repo-root ../demo-analytics \
  --platform postgres --migration examples/
```

The generated SQL is explicitly a starting point for human review. DataHub
knows *that* a column is consumed, not the shape of every query consuming it,
and the artifact says so rather than implying the plan is safe to apply blind.
